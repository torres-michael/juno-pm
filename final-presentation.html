What I built

Five modules, one AI Associate PM

Each module added one piece. Together they define what the AI does, what it is allowed to do, and what good looks like.

Module 1
Skill file
Role

You are Juno PM, an AI Associate PM supporting RocketShip's Growth team. In this skill you act as the team's experiment status analyst. You work from experiment data provided from Jira, Optimizely, and Hex, and you have read-only access to all three. Your output feeds the team's experiment dashboard and the recommendation skill, so it has to be accurate, complete, and consistent every time. You do not act on your own. You never change feature flags or traffic allocation, edit Jira tickets, or message anyone. You never fill a missing value with an estimate. You never recommend Ship, Keep running, Scale or Kill a variant; that call belongs to the Recommendation skill.

Task

Using the experiment data provided from Jira, Optimizely, and Hex, aggregate the status and results of every running experiment into one reliable view. Give the team a single, trustworthy picture of what is live, how each test is performing, and which experiments have data that can't be trusted yet. Report what is true and what is broken, not what to do about it.

Module 2
Prototype
Prototype

https://juno-experiment-dashboard.lovable.app/

What it demonstrates

Testable assumption: If the Experiment Status skill's output (Module 1) is shown as one view, a growth PM can tell in under 2 minutes which experiments are live, which have data they can't trust, and which need a decision. Today, getting from Jira, Optimizely and Hex to a call on every running experiment takes 1 to 3 hours each morning, and this triage step is the first part of that time.

The one flow it proves: morning triage. Open the dashboard → the alert banner shows which experiments have untrustworthy data → the summary cards show what needs a decision → click a row to see the evidence, with each value labeled by source and refresh time.

Design choices it tests:
- Three metric layers. Input (the controllable metric), primary (revenue) and guardrail (lead quality as the early warning). GRO-104 shows why this matters: form completion up 6.4pp, but revenue P(beat) 4% and lead-quality P(harm) 97% → Conclude to control.
- Colors come from code, not AI. Green, yellow, red and gray "Too early" are fixed thresholds from `thresholds.json`, and anyone can audit them. The AI only proposes the recommendation, and a human decides.
- No recommendations on bad data. When a source fails to update or data conflicts, the recommendation is paused and the experiment appears in a "failed to update" alert.

Debrief

- What worked:
- The build matched the spec on the first pass. All 18 experiments load, the banner shows 6 data issues, and the summary cards are correct (4 ready for a decision, 5 too early, 2 past due).
- Every edge case rendered as designed: the Jira/Optimizely conflict (GRO-116), the missing planned split (GRO-118), the experiment with no Jira ticket (GRO-120), the missing guardrail (GRO-128), the 4-variant test with one arm to cut (GRO-109) and the killed variant (GRO-107).
- The GRO-104 row tells the input → output → guardrail story at a glance. It's the strongest demo moment.
- Pausing recommendations on bad data felt trustworthy, not broken. The banner plus "Learn more" turns a failure into a task.
- What broke / felt like a toy:
- Two sources of truth for derived numbers. The UI says GRO-112 is on "Day 10 of 22", while the AI recommendation says "day 9 of 14 minimum". The app counts days inclusively and the recommendation counts them exclusively. If the UI and the AI can disagree about a fact, PMs will stop trusting both.
- Stale rows still show confident colors. GRO-113's Hex data is 2 days old, but its input still shows a green "P(beat) 98%". The recommendation is paused, but the metric chips aren't.
- Every row says "Needs human decision", including "Keep running", so the tag stops meaning anything.
- The most important columns are hardest to see. Primary, Guardrail and Recommendation sit at the far right and scroll off-screen on a laptop-width window.
- It's a snapshot, not a morning tool. It uses static JSON, mocked recommendations, no "what changed since yesterday" view, and no links into the real tools. It shows today's state but not what's new.
- What I'd change next pass:
1. Compute all derived values (days running, sample progress, past due) once in the status skill's output, and have both the UI and the recommendation skill read them, never recalculate them.
2. Dim or gray out the metric chips for any experiment with a data issue, not only the recommendation.
3. Show "Needs human decision" only on actionable calls (Ship, Scale, Cut variant, Conclude to control).
4. Reorder the columns to Experiment → Recommendation → Primary → Guardrail → Input, and move dates and traffic into the drawer.

Module 3
AI PRD
Problem and user

RocketShip's growth PMs make a call on every running experiment each morning, because they need to know quickly whether a test is making or losing money. Getting to those calls takes 1 to 3 hours, about 2 on a typical day, depending on how many experiments are running. PMs pull numbers from Jira, Optimizely and Hex, work out which experiments are healthy, which have bad data and which need a decision, and then build each recommendation from scratch. Data problems go unnoticed in the process.

Juno handles that triage with three skills: Status (one trustworthy view of every running experiment), Recommendation (a proposed action with a number-backed reason) and Learnings (draft write-ups of concluded tests). It works inside limits a human set on purpose, and a PM makes every decision.

Permissions

The permission tier

| Side-effect class | Tier |
| read | auto |
| draft | auto |
| write | confirm |
| send | blocked |

Justification

Read: auto. All reads are against Jira, Optimizely, Hex, thresholds and the learnings log. The worst case is wasted tokens or a stale pull, and stale data is already labeled and pauses recommendations. Nothing changes in any system.

Draft: auto. Snapshots, recommendations and learning drafts appear only on the dashboard, each tagged "Needs human decision." A wrong draft costs a PM a few seconds of reading, and nothing is acted on until a person decides. Making drafts confirm would mean approving 20 items every morning to see your own dashboard, which brings back the triage work Juno exists to remove.

Write: confirm. `publish_learning` puts a conclusion into the team's permanent record. A wrong learning ("annual-plan nudges don't work") can quietly kill future tests. Undoing the page is easy, but undoing the belief isn't. A PM approves every publish.
*Exception:* `route_to_human` runs auto. It only adds the experiment to the owner's decision queue with a reason, can be cleared in one click, and an escalation that waits for approval defeats its purpose.

Send: blocked. No send verbs exist in V1: no ship, kill, traffic change, conclude or Slack post. Changing a live experiment changes what customers see and what revenue we book, and rolling back a flag doesn't recover a week of lost signups. Mistakes would be both irreversible and widespread, so this stays blocked no matter how the evals look. Revisiting it is a V2 decision.

Module 4
Agent control panel
What it is doing

Juno's Recommendation skill reads the verified daily status snapshot and proposes one action per running experiment (Ship, Keep running, Scale or Kill a variant), with a reason that cites the numbers behind it, so each growth PM starts the day with a ready decision queue.

Rules of engagement

Agency Permission:

Decides alone (auto):
- Read the status snapshot and thresholds.json
- Draft a recommendation and show it on the dashboard, tagged "Needs human decision"
- Route an experiment to the owner PM's decision queue (route_to_human)
- Pause itself: withhold a recommendation and label why

Proposes and waits:
- Every action (Ship, Keep running, Scale, Kill variant) is only a proposal. The PM makes the change in Optimizely.

Cannot do at all (no tool exists):
- Ship, kill, conclude or change traffic on any experiment
- Edit Jira status or thresholds.json
- Post to Slack or notify anyone outside the Juno dashboard

Access Control:

Reads only:
- The daily status snapshot for experiments on the self-serve growth team
- thresholds.json (read-only, versioned)

Cannot reach:
- Jira, Optimizely or Hex directly (only the Status skill can), so it can't route around a data flag
- The Learnings Log, other teams' experiments, raw warehouse data, Slack, customer-level data, roadmap or sales docs

Visibility: every recommendation is visible to the whole growth team, not just the owner PM. Juno keeps no per-PM memory.

Fallback Protocols:

- Data flag on the snapshot → no recommendation; label the flag; route_to_human
- Same tool fails 2x in a row → stop; "Failed to update"; route_to_human. No third attempt.
- Verifier fails → replace with "Paused: Juno couldn't verify this recommendation" + failed rule; route_to_human. No retry.
- Turn limit (4) or 60s timeout hit → "Incomplete: turn limit reached" or "Paused: run timed out"; no recommendation; route_to_human
- thresholds.json unreadable → fail closed: no colors, no recommendations for anyone this run
- Spend hits $0.15 per experiment or the $15 daily cap → stop; refreshes disabled until the next scheduled run, with the reason shown
- Every fallback is visible on the dashboard and added to the eval test set. Nothing is dropped silently.

Checkpoints:

1. Before any recommendation is shown: the verifier pass (automatic, every time)
2. Before any Medium-confidence item is shown (any Ship, borderline guardrail, input/primary disagreement, any Kill or Scale, past end date): owner PM reviews in the decision queue
3. Before anything changes for customers: a PM acts in Optimizely. Juno never does.
4. Weekly: human reviewers score a sample of verified recommendations against the eval rubric. If the verifier agrees with reviewers on <95% of checks, or one bad recommendation reaches a PM, swap in a code-based check. If >10% of recommendations fail verification in a week, pause the skill until a PM reviews the prompt.

Module 5
Human eval rubric
What I score

Juno's daily experiment recommendation. That's the single action the Recommendation skill proposes for each running experiment (Ship, Keep running, Scale, or Kill a variant), with its cited reason. When Juno can't support a call, the "Paused" result it shows instead counts too. Before standup, tell me what to do with each running experiment. Give me one action backed by numbers I can check in the snapshot, or tell me plainly that the data can't support a call yet.

Pass bar

An average of 4 or higher on Right call and on Ready to act, no single Right call score below 3, and Stays in bounds passes.

Fails outright, whatever the average:

- Evidence accuracy: any "no"
- Knows when to hold back: any "no"
- A Ship, Kill, or Scale shown without going to the owner PM for review first
- Any wording that says or implies Juno made the change itself (e.g., "shipped," "killed the variant")
- A paused result with no reason shown

Module 6

How I’ll know it’s working

The goal the AI is meant to move, where it stands today, and the result that would make me stop.

The goal

Growth PMs make their daily call on every running experiment faster, using Juno's trusted dashboard, recommendations and learnings, instead of pulling data from Jira, Optimizely and Hex by hand and working out what it says.

Baseline

About 2 hours each morning (1 to 3 hours, depending on how many experiments are running) from opening the data to a call on every running experiment.

Target and review date

30 minutes or less on a typical morning, checked Friday, January 15, 2027, six weeks after the December 1 launch.

Usage metric

Acceptance rate: the share of Juno's recommendations the owner PM follows without overriding. Target: 70% or more.

Pattern I’ll watch for first

People stop relying on answers. After a visible wrong call, most likely a Ship, acceptance drops 15 points or more week over week and PMs go back to checking Hex by hand.

Stop line

If morning decision time is still 90 minutes or more on January 15, Juno isn't removing the manual work. Turn it off.

Reflection

What I learned

Where it was hardest, what I’ll keep doing, and the moment my thinking changed.

Friction

The hardest part was telling where one framework ended and the next began. The skill, the harness and the control panel overlap: my PRD's loop and the control panel's stop conditions both say when Juno stops, so at first I couldn't see what each one added. What clicked was that the harness sets the limits, meaning what Juno can see, do and remember, and the control panel sets how it decides on its own inside those limits. My takeaway is to get sharper about when each one is actually needed at work, so I use them when they help and don't stack them on problems that only need a good prompt.

Key learnings

The habit I'm keeping is the most basic one: writing dedicated skills for the repeatable tasks I do every day. Juno showed me that a well-written skill is the foundation everything else builds on. Once those are documented, I can rethink my day-to-day workflows and start building agents that complete tasks for me, instead of me prompting Claude by hand each time. Skills first, then the harness and agents on top, only where the task earns it.

Aha moment

My biggest aha was how different an AI PRD is from a traditional one. A traditional PRD defines deterministic logic: if the user does this, then the product does that. An AI is non-deterministic, so the PRD's job changes from scripting behavior to setting boundaries the AI can safely act within on its own: what it can see, what it can do, when it stops and what a human has to approve. That's a new muscle I need to build as a PM. A second, smaller aha: terms I'd seen all over LinkedIn, like harness, skills and evals, finally clicked once I'd built them myself. Now I understand what people are actually talking about, and I can judge when it applies.
